# Работа агентов

1. Прочитай `.coord/repository.json` и только назначенную карточку `.coord/tasks/<ID>.json`. Историю и тематические docs читай по необходимости.
2. Выполни `git status --short`, `git fetch origin` без prune и `git branch --show-current`. Не перезаписывай чужую незавершённую работу.
3. Новая задача начинается от свежей интеграционной ветки из repository.json, в своей `task/<ID>-<name>`. Не продолжай случайную старую claude/* ветку. Локальное имя `work` не даёт разрешения на push в опубликованную ветку.
4. Перед работой запиши точный base SHA в карточку. Только координатор назначает owner и allowed_paths. Общие файлы и перекрывающиеся задачи выполняются последовательно.
5. Меняй только выделенные файлы. Понадобился общий файл — передай точный запрос координатору. Не копируй папку src или dist поверх другой версии.
6. Запрещены force push, reset чужой ветки, удаление удалённых веток/тегов, смена default branch и публикация сайта без отдельной задачи на это. dist не коммитить.
7. Перед сдачей обнови base из origin; сохрани обе стороны интеграции. Выполни `node scripts/repo-check.mjs --task .coord/tasks/<ID>.json`, build и подходящие тесты. При слиянии чужих изменений различай их и собственный diff.
8. PR — в интеграционную ветку. В описании: задача, base SHA, head SHA, что изменено, проверки, ограничения. Каждая новая версия требует QA своего SHA.
9. Kimi проверяет точный SHA. QA и материалы храни в отдельных task/SHA каталогах или CI artifacts. В финале дай краткую сводку и пути; не пересказывай весь репозиторий.
10. Координатор последовательно объединяет PR, проверяет результат объединения и назначает его SHA для итогового QA. Публикация — отдельный выпуск после визуального одобрения пользователя именно этого SHA.

Эти правила не заменяют GitHub rulesets и защиту production environment.
