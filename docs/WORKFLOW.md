# Текущий рабочий процесс

Единственная интеграционная ветка указана в `.coord/repository.json`:
`claude/friendly-archimedes-onmybq`. Остальные старые claude/* — исторические;
новые задачи от них не начинать. main пока не существует. Переименование
не требуется для разработки: база определяется конфигурацией, а не именем.

## Задача

Координатор назначает `.coord/tasks/ID.json`: владелец, отдельная `task/ID-name`,
полный base_sha, allowed_paths и критерии готовности. Одновременно один файл
изменяет один агент. game.ts, ctx.ts, lock-файл и workflows распределяются
последовательно. Карточка — средство координации, не распределённая блокировка.

Рабочий старт: git status, git fetch origin (без prune), свежая интеграционная
база, отдельная ветка/worktree. Если среда создала локальную ветку work,
это не разрешение отправлять её в интеграционную ветку. Не терять dirty-файлы.
Перед сдачей обновить интеграционную базу, сохранить обе стороны изменений,
обновить base_sha карточки и проверить собственный diff.

## Сдача

- `node scripts/repo-check.mjs --task .coord/tasks/ID.json`
- `npm run build` и подходящие существующие тесты.
- PR только в интеграционную ветку. Коротко: задача, base/head SHA,
  результат проверок, ограничения. Не нужно пересказывать всю историю.
- CI Verify candidate проверяет объединённого кандидата, build, statics,
  resting и сам guard. Он не проверяет визуальный стиль и реальный FPS.

## Локальный QA

Kimi получает PR и полный SHA, скачивает код сам через Git, желательно в
отдельный worktree. Файлы вручную не переносить. Пока автономный запуск Kimi
не подключён, пользователь передаёт ему ссылку на PR; остальное делает Kimi.
Node/npm, браузерные тесты, console/video и измерения на локальной машине
ещё должны пройти проверку возможностей. Их нельзя объявлять работающими заранее.

Результат: `test-results/ID/SHA/QA_REPORT.txt`, рядом screenshots/logs/video.
Поля: SHA, окружение, выполненные сценарии, ошибки и шаги, доказательства,
непроверенное, способ замера производительности. PASS только с доказательствами.
Малой задаче достаточно короткого отчёта. Результаты передаются координатору
через пользователя, PR-материалы или согласованное общее хранилище;
локальная папка сама по себе другим агентам не видна.

## Интеграция и выпуск

Координатор объединяет PR последовательно. Итоговый интегрированный SHA
проверяется перед выпуском; изменение кода после QA требует новой проверки.
Обычный push больше не публикует сайт. Release approved version запускается
от интеграционной ветки с полным ранее проверенным и визуально одобренным SHA.
Сборка получает version.json с SHA и номером workflow run.
Текущий сайт при внедрении этих правил не пересобирается и не заменяется.

Выпуск производится только по явному поручению пользователя после приёмки.
Ручной workflow не является автоматической проверкой QA: координатор сверяет
SHA отчёта и одобрения. Старый одобренный SHA можно выпустить для отката без
перезаписи Git-истории. Один выпуск за раз: concurrency не является FIFO.

## Границы защиты

Guard ловит потерю обязательного коммита оптимизации физики, но наличие
предка не доказывает сохранение поведения. Нужны diff-review и тесты.
Текстовые правила и CI без branch rulesets не запрещают администратору
прямой push или обход проверок. Настройки запрета force push/удаления,
обязательных PR/checks и среды публикации управляются отдельно в GitHub.
При общей admin-учётной записи технически различить агентов невозможно.
Запрещено заявлять, что серверная защита включена, без её проверки.

Не удалять старые ветки, не выполнять force push, не менять default branch
или политики доступа в рамках обычной игровой задачи.
